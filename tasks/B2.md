# B2 — Freshness guarantee + inline status toggle

## Task (delivered verbatim, identical to every framework arm)

> Add an inline status toggle to the invoices table, and make every
> surface of the app show current data after any change.
>
> - An invoice's status can be switched between paid and pending
>   directly from its row, in both the desktop table and the mobile
>   card layout, with instant feedback and the change persisted.
> - After ANY change to invoices — create, edit, delete, or status
>   toggle — every surface that displays data derived from invoices
>   shows the current values immediately: the dashboard cards
>   (collected, pending, invoice count), the latest-invoices list, the
>   invoices table, and the pagination counts.
> - This includes surfaces reached by back/forward navigation and by
>   navigating away and back: no view may show stale invoice data, at
>   any point, under any navigation path.
> - Existing behavior — search, sorting, pagination, URL persistence —
>   is unchanged and composes with the toggle.

Deviation from the ladder text, recorded: the ladder's B2 sketch listed
the revenue chart among the surfaces; the `revenue` table is an
independently seeded aggregate in this schema, not derived from
invoices, so it is excluded from the requirement rather than asking
both sides to fake a derivation.

## Acceptance (verified by the harness, not the building agent)

1. Toggle works from desktop row and mobile card; UI reflects the new
   status without a manual reload; the change is in the database.
2. Dashboard cards + latest invoices reflect a toggle/create/delete
   made on the invoices page, when reached by: (a) client-side nav,
   (b) browser back/forward, (c) fresh deep load.
3. The zero-staleness path specifically: mutate → navigate → back —
   no surface anywhere shows pre-mutation numbers.
4. Search/sort/pagination unchanged (B1 acceptance spot-checks pass).
5. Production build passes; both sides deployable.
